# Auto 节点模型细分设计建议

> 职责布局已更新：常用职责数量与配置界面以 [18～20 个职责位的模型中心布局](2026-10-07-auto-model-duty-layout.md) 为准。本文早先的无数量上限职责菜单及 29 类初始分类建议已被替代，下面的分类表仅保留为历史节点用途拆分参考。稳定定义身份、协议传递、未知映射、配置迁移和执行绑定章节继续作为待定案的实施约束参考。

> 日期：2026-10-07。状态：历史协议建议。18/20 职责布局已进入源码实施，配置与行为以 [实施契约](2026-10-07-auto-duty-routing-implementation.md) 为准；下文未限数量的菜单与“当前代码仍为五阶段”描述只记录当时状态。

## 结论与目标

五个模型组不足以表达当前工作流。调查、需求、设计、实施计划应独立；设计审查、代码审查、实际验证和交付稽核也有不同的输入、产物与能力要求。继续把这些任务塞进 plan 或 review，会限制用户按真实职责选择模型。

推荐采用“可扩展职责类型配置固定模型，具体节点可以单独覆盖”。类型和节点覆盖均不设固定数量上限。职责数量不等于不同模型数量：多个类型可以引用同一个实际模型配置，不必复制配置或人为增加模型种类。

目标是让每次 Auto 调用都能说明：哪个工作流的哪个节点、明确承担什么职责、从哪个配置来源选模、实际发往哪个模型与渠道。同一节点执行中的目标和请求前缀保持稳定，再用上游实际总费用及任务质量评价收益。

## 配置结构与可见行为

### 职责类型：提供可复用的默认模型

职责类型是工作流创建或人工绑定时明确声明的任务类别，例如 `investigation`、`design`、`implementation_plan`。每种类型选择一个具体启用的模型配置，包含实际模型 ID、渠道、接口及请求参数。不能引用会轮询切换成员的模型组。

类型用于复用配置，不承担语义判断。代理不读取提示词猜类型，不按文本长度、工具动作或每轮 Agent 名称切换模型。用户可以新增类型，也可以把已有类型拆成更细的类型。

建议前端首先展开这些常用职责；其余职责放在可展开列表中，始终允许新增：

| 常用职责 | taskType | 主要产物或行为 |
|---|---|---|
| 主控协调 | `orchestration` | 分配任务、衔接工作流 |
| 调查取证 | `investigation` | 代码、日志、调用链与证据报告 |
| 需求整理 | `requirements` | 目标、约束与验收标准 |
| 技术设计 | `design` | 架构、接口和实现方案 |
| 实施计划 | `implementation_plan` | 可执行步骤、范围和验证安排 |
| 代码实施 | `implementation` | 修改代码、局部修复与相关验证 |
| 设计审查 | `design_review` | 需求与设计问题、审查结论 |
| 代码审查 | `code_review` | 实际改动中的问题与审查结论 |
| 实际验证 | `validation` | 测试、构建、E2E 与验收结果 |
| 交付稽核 | `delivery_audit` | 核对产物、验证证据与完成情况 |
| 收尾整理 | `finalization` | 交付说明与结果整理 |

这是起始展示建议，既不是数量上限，也不是要求每个工作流必须依次执行这些职责。准备、运维、实验、清理、PR 提交和反馈处理等可分别配置。

### 节点覆盖：同类节点也可以选不同模型

“节点配置”页按工作流定义及节点路径显示每个真实 step，展示原始 nodeId、职责类型、有效模型、渠道与选择来源。每个节点允许覆盖其类型的模型；取消覆盖后恢复使用类型配置。

推荐选择顺序：

1. 该稳定节点身份的明确模型覆盖。
2. 该节点创建时明确声明或人工绑定的职责类型所配置的模型。
3. 用户明确配置的固定默认目标，记录未知原因，并进入未归类清单。

即使同属 `code_review`，A、B 两个独立审查节点也能各自绑定不同模型。此功能应作为基础能力，避免同一类型强制覆盖全部审查分支。

Auto 的模型选择来源必须优先于 Kiro 合成工作流中的初始模型或分组模型。普通子 Agent 继承父调用的 Auto 绑定；进入独立声明的新工作流节点时，才按该节点重新选择。明确手动选模的请求仍遵循手动选择。

### 未归类清单：让缺失映射可见

新节点没有明确声明、定义无法对应或职责配置缺失时，记录原始身份和原因，显示此次采用的固定默认目标。不能把未知节点伪装成 `run`，也不能悄悄换成其他模型。默认目标失效时报告配置错误。

对已经具备稳定定义身份及节点路径、仅缺职责的节点，用户可以绑定已有职责、创建新职责或直接设置节点覆盖。此时有明确覆盖就使用覆盖，职责缺失仍保持可见。缺少稳定身份或定义无法可靠对应时，只使用固定默认目标并报告原因；先建立稳定身份，才允许保存长期职责绑定或模型覆盖，不能按裸 nodeId 暂存例外。

## 必须真实拆分的工作流边界

### 调查、设计、计划分别成为节点

只有配置条目变多，还不能把一个 Agent 调用内部的调查和设计变成不同模型。推荐在工作流定义中形成明确边界，例如：

`investigate -> requirements -> design -> design-review -> implementation-plan -> implement -> review -> validate -> final-audit -> finalize`

这条链是设计示例，按实际任务省略不需要的节点。调查输出证据，设计消费证据与需求，计划消费已确定设计；各节点独立绑定模型，在节点内部固定使用。

当前 `plan` 的定义可能同时调查、整理约束与制定计划；表中 `implementation_plan` 表示其整节点主要目标，不表示已把调查环节拆出去。想分别选模，就要把这类工作流改为独立调查节点与计划节点，不能从中途“读文件”推定进入调查阶段。`audit-plan` 目前也只能作为一个混合节点配置。

`work`、`iterate`、`experiment`、`respond`、`native-code-verify` 等 step 也包含多类工作。当前可以给整个节点设固定模型；如果确有不同能力或成本需求，再修改工作流形成多个真实节点。设计职责可以进一步拆分，如接口设计与架构设计，但拆分同样需要明确工作边界。

### 同名 run 不能靠 Agent 名称归类

本机 29 份合成 `run` 定义中，planner 7 份、coder 19 份、reviewer 3 份。同为 planner 也可能承担调查或计划，因此撤回此前 `agent://wf-planner` 一律映射 plan 的建议。

推荐在已核实的创建入口明确职责：普通主聊天声明 `orchestration`；为调查创建的合成 run 声明 `investigation`；为计划创建的 run 声明 `implementation_plan`。其他职责同理。`general_agent` 仅用于确实明确声明为通用执行的节点，没有声明时保持未知。

当前尚未证明这些工厂已有可直接使用的职责字段。实施时要核实创建与传递位置，不能把运行时 `agentMode` 当作职责证据。明确绑定表可以承载分类，无须恢复旧的角色选模配置。

### 多模型审查保留固定分支

`feature-pipeline` 的 `review-fable`、`review-gpt` 原定义分别声明 `claude-fable-5`、`gpt-5.6-sol`。`semantic-review-multi-model` 的 `review-opus`、`review-gpt` 分别声明 `claude-opus-5`、`gpt-5.6-sol`。这是定义声明，不能据此证明真实出站模型。

新设计允许分别对两个节点设置固定覆盖，保留异构审查。两套 recipe 中同名 `review-gpt` 的覆盖必须分开保存。多个节点引用同一模型时，界面应如实显示，不再称其为不同模型交叉审查。

`aggregate` 合并 issues-only 报告；`code-aggregate` 还核对计划完成度并给出 verdict，适合分别配置。`validate` 执行实际验证，`final-audit` 只读核对交付证据，`finalize` 整理交付，三者也应分别配置。

## 当前实现限制与接通要求

当前事实：

- `store/auto_routing.go` 硬编码五个 `stage_models`，解析器要求五项并拒绝未知字段。
- `tools/kiro_stage_bridge.mjs` 直接把 `workflow.nodeId` 当作 `stage`，缺失 nodeId 时会设为 `run`。新协议必须区分明确声明的普通主聊天与身份缺失的工作流节点，后者不能用 `run` 掩盖缺失。
- `converter/workflow_stage.go` 的 v1 私有头只接受 `version`、`stage`、`workflowId`、`conversationId`、`agentMode`、`agentContinuationId`。
- `router/auto_policy.go` 仅用五个同名值取模型；未知或缺失值采用固定 `default_model_id`。
- 现有锁在当前工具续轮中复用同一 stage/workflow 的目标，尚不能证明整个节点执行都固定。

因此，本方案需要同步调整工作流分类来源、桥接协议、存储、后端路由和前端。只增加下拉框，或者把更多 nodeId 翻译成旧的五阶段，无法实现上述行为。

### 配置身份与运行身份分开

建议长期配置键使用稳定的定义身份、定义修订及规范化节点路径：保留嵌套与分支路径，剔除循环迭代编号。只有定义确保 nodeId 全局唯一时，才可以简化节点路径。定义修订发生变化时，核对已有绑定是否仍适用，不能无证据把旧路径覆盖迁移给新节点。

不能使用裸 nodeId、显示 workflowName 或每次运行生成的 workflowId 作为长期配置键。运行时 workflowId 用于关联执行。哪些稳定定义标识能在本机工厂中获得或建立，尚需实施时核实。

新私有元数据应明确区分原始节点、稳定定义身份、节点路径、明确职责、运行 workflowId 与节点执行实例。字段名与协议版本需要实施时定案；当前 v1 不支持直接新增未知字段。Kiro 工作流 JSON schema 的扩展方式尚需核实，不能直接插入未经支持的属性。

### 整节点执行绑定

建议首次调用时保存有效模型配置、实际模型、接口、渠道及请求参数的执行绑定；该节点执行内的模型续轮、工具返回与重试复用绑定。进入新节点执行时重新选择，配置修改对新执行生效。

循环中的下一次节点执行可以重新读取配置，但不能仅因为请求轮次增加就创建新绑定。并行节点必须拥有独立执行身份。普通子 Agent 继承父绑定；声明了独立节点职责的子工作流按自己的节点绑定。

实现这个保证需要证明执行实例身份、迭代边界和结束信号。`this.executionId` 虽出现在调用 metadata 中，其生命周期尚未证实，不能直接认定它就是整节点锁键。绑定目标失效时明确报错，不静默换模型、渠道或降低请求参数。

### 可核对的日志

每个 Auto 请求记录运行关联 ID、稳定节点身份、原始 nodeId、明确 taskType、分类来源、覆盖来源、有效 modelConfigId、实际上游模型、脱敏渠道身份、执行绑定是否复用，以及未知原因。敏感凭据不进入日志。

由此才能分清：初始模型未被 Auto 接管、节点没有分类、节点已分类但目标错误、重试复用、正常多轮工具调用与真实重复请求。不能仅根据同一模型出现多次判断没有接通 Auto；多个类型可能刻意引用同一模型。

## 缓存与费用的配置原则

细分职责给用户更准确的选模能力，不自动提高缓存率。类型数量增加不影响缓存，实际模型、渠道、请求前缀与调用间隔改变才可能影响上游缓存复用。若所有职责各用不同模型，可能分散调用，减少各模型可重复的共同前缀；不应把“每类都用不同模型”当作必然省钱的规则。

建议先保留少量实际模型配置，调查与设计可以分别配置，即使开始时都引用同一个模型。后续按质量、重试和费用证据单独调整某个职责；确有独立能力需求的节点再设覆盖。不要同时修改模型、渠道、effort 与提示词，以免难以判断收益来源。

优先稳定同节点多轮请求的静态 system prompt、工具定义及顺序、历史追加方式。不同职责的必要提示词与工具不能为了缓存而删去。私有路由元数据不加进提示词；不把 taskType、节点名、迭代编号或每次执行 ID 加进缓存键主动分裂缓存。

此前核对的实际模型为 `cn:deepseek-v4.1-flash` 与 `gpt-6.1-sol`，后者界面名为 `gpt-6-astra1`。两份本地费率配置均为普通输入 5、输出 30、缓存读取输入 0.5 USD/百万 token；上游真实费率尚未核实，不能按界面名称或本地估算判定哪种模型更便宜。

收益以完成同类任务的上游实际总费用为主，同时比较质量、完成率、耗时、模型轮次、输入量、缓存读取量、输出量与重试。区分按请求条数的命中率和按输入 token 的缓存比例，缓存率上升不保证总费用下降。当前转换通路中已有的 `prefix_audit` 不能代表所有接口已具备等价观测。

## 实施顺序与验收

实施前还需明确版本化配置迁移契约：保留原始五槽配置的可恢复快照，列出旧值到新职责的明确迁移表；不能自动把旧 plan 模型填入所有调查、需求、设计职责而伪称已完成独立配置。缺少的新配置要保持可见，按明确固定默认目标处理。迁移失败保留原配置并报告原始错误，不覆盖成半成品；回滚时恢复旧版可读取的原始配置，不让旧解析器读取新格式。备份用于恢复，不参与新路由。具体迁移表与配置版本仍待实施前定案。

1. 按本建议确定职责类型与节点覆盖契约，标记混合节点；需要分模的调查、设计、计划先有真实节点边界。
2. 核实稳定定义身份、创建声明与执行生命周期，同步升级桥接元数据和后端解析。
3. 把五项硬编码存储改为可扩展职责配置和节点覆盖，路由按明确优先级选模，并记录选择来源。
4. 核实并实现整节点执行绑定及子 Agent 继承，保留固定审查分支。
5. 前端提供职责配置、节点有效目标与覆盖、未归类清单；常用职责展开，其余折叠，允许新增和拆分。
6. 由用户运行真实工作流，再以日志核对节点切换、工具续轮、循环、并行、子 Agent 和未知节点行为；按上游账单评价收益。

后续实施的最低验收条件：调查、设计、计划能分别命中各自配置；同名 run 的不同明确职责可分别选模；同一审查类型的 A/B 节点可保持不同固定模型；混合节点内部不猜测换模；工具续轮和普通子 Agent 保持绑定；新节点缺失分类在界面和日志中可见；职责扩展不要求修改五槽枚举。

本次细分方案仅新增、修订两份建议文档，没有实施本方案的 Auto 运行代码、数据库或 Kiro 安装文件变更，也未编译、运行测试、部署、重启、提交或推送。工作区此前已有的未提交代码改动继续保留，不代表本细分方案已接通。完整协议与整节点执行绑定仍是待实施能力。
