## 官方公开行为

核对日期：2026-10-06。来源为 [Kiro Models](https://kiro.dev/docs/chat/model-selection/) 和 [Kiro 定价与 FAQ](https://kiro.dev/pricing/)。Models 页面标注的更新日期也是 2026-10-06。

官方 Models 写明：选择 Auto 后，让 Kiro 为每个任务自动路由到合适的模型（“route each task to the optimal model automatically”），在质量和成本之间取得平衡。定价 FAQ 补充，Auto 是一个结合多个前沿模型、特定任务的专用模型、意图识别和缓存等技术的 agent。这说明 Auto 包含任务识别与模型选择；故障转移只是本地代理已有的执行能力，不能代替任务选模。

官方没有公开任务分类器的提示词、类别表、完整的类别到模型映射、切换阈值或内部模型轨迹。不能把官网的人工选模建议当成已公开的 Auto 实际算法，也不能从当前日志中只有 `modelId=auto` 的响应猜测底层型号。

## 官方使用建议

下表是官网给用户的人工选模建议，不是 Auto 内部映射规则：

| 使用场景 | 官方建议 |
| --- | --- |
| 大多数日常开发工作 | 从 Auto 开始，自动平衡质量与成本。 |
| 最难的多步开发、长时间重构和复杂终端任务 | GPT-5.6 Sol。 |
| 日常多步工作，关注吞吐或成本 | GPT-5.6 Terra 或 Luna。 |
| 复杂问题遇到阻碍、持续多文件工作、需要更强自检 | Opus 5.5。 |
| 范围明确的编码、修 bug、复审或文档任务 | Sonnet 5.5。 |
| 简单修复、快速迭代、节省积分 | Haiku 4.5。 |

模型下拉框的选择应用于对话的后续消息。官方另建议在账户设置中观察实际用量；支持推理强度的模型可以调低 effort 来降低内部思考 Token 消耗。相同积分倍率不保证同一任务消耗相同积分，因为 Token 数、分词方式和内部思考深度可能不同。官方 Auto 的 1.0x 是官方相对计费基准，不是本地 USD 单价。

## Credits 显示与计算边界

官方 FAQ 明确：积分按第二位小数计量，任务的最小消耗为 0.01 Credits。此前抓包的 `meteringEvent.usage` 包含更多小数位；这并不说明官方最终账单也按这些位数展示。官方未在这些页面公开原始帧到最终账单的舍入时点与完整公式。

用户已选择本地估算积分为配置费用 USD ÷ 0.04。管理界面 Credits 统一显示两位小数；计算、原始日志、接口小数精度字段和数据库累计继续保留原始精度，避免逐帧舍入再求和造成偏差。USD 分项仍显示六位。仅凭官方最低 0.01 的说明，不给本地估算新增未经确认的逐帧最低收费或舍入扣款规则。

## 复核时的实现缺口与本次修正

复核时调用链为 `ParseKiroRequest -> router.Resolve(modelId) -> Forwarder`。本次早先增加的 `Resolve("auto")` 只选同名启用分组/模型或默认候选；它没有接收任务信息，所以不能判断“哪种事应该使用哪个模型”。现在 Kiro Auto 主请求改走 `ResolveAuto(ParsedConversation)`，直接消费结构化任务与能力信号，其余路径保留原语义。

请求解析层已有 `AgentMode`、`AgentTaskType`、`ReasoningEffort`、图片、工具定义、工具结果及主会话/分支的 `ContinuationStateKey`。这些是可以用于本地策略的输入。现有 `simple-task` / `intent-classification` classifier 路由只是转发 Kiro 的独立分类请求，并没有读取分类结果来决定后续主请求模型。

早期动态模型讨论稿已从当前目录清理，历史内容可从 Git 历史恢复。当前行为以[无补丁 Auto 与 activity 观察契约](2026-10-20-activity-driven-auto-routing.md)为准，activity 异步观察不构成首轮同步身份。以下实施和验证记录仅描述本文当时范围。

## 本地适配方式的选择

此前比较了以下方式；用户已选择第 1 种：

1. **明确任务字段与能力规则**：根据请求的任务角色、图片需求、工具状态、推理强度和上下文需求，选择已明确配置能力的模型。规则应记录命中原因和实际模型；不能只看模型名字猜能力，也不能因为请求列出工具就认定当前一定是复杂编码任务。
2. **小模型语义判断**：在主任务执行前增加分类调用，由它输出受约束的任务类别，再映射到已配置模型。需要确定分类模型、输出契约、失败处理和缓存；额外分类费用与延迟应纳入统计，不得在分类失败时静默更改用户语义。
3. **保留官方 Auto**：继续抓包/直通官方，由官方执行任务识别和调度；本地只能报告已公开的模型标识和官方计量值。

若选择本地任务选模，需沿用已有讨论稿的工具链与缓存约束：同一次流式输出固定实际模型，工具结果回传保持同一执行域；主会话和独立 agent 分支分别识别。严格保留缓存与故障时允许其他模型冷启动接管存在取舍，需明确后才能实施。最终按实际成功候选记账，并保留请求 `auto` 标识、任务类别、选模原因和切换记录。

## 首版实施契约

设置键为 `auto_routing_config`，值为 JSON 字符串，不新增数据库表。配置包括 `enabled`、`default_model_id`、`vision_model_id`、`reasoning_model_id`、`long_context_model_id`、`fast_model_id`、`fast_max_chars`（默认 500）、`long_context_min_chars`（默认 32000）和 `task_rules`。每条任务规则包含 `field`、`value`、`model_id`；field 只允许 `agent_task_type`、`agent_mode`、`chat_trigger_type`，值去首尾空白并忽略大小写精确匹配，规则按列表顺序生效。目标必须为启用的实际模型配置 ID，不要求建立 Auto 分组。能力角色由用户明确配置，不根据 provider 或模型名猜测。

仅对 Kiro 主生成请求的 `modelId=auto` 生效。手动选模、兼容 API 的精确匹配和 Kiro 独立 classifier 的执行模型规则保持原语义。未启用策略时仍是旧有兼容默认路由，Kiro 模型列表明确标为 `Auto（默认路由）`；启用后标为 `Auto（按任务选模）`。管理界面的“模型配置”以独立固定首行提供 Auto 内置默认配置入口，点击后在弹窗中设置策略开关、能力目标与任务规则；该行不能删除、测试或停用，不进入真实模型统计或筛选，也不自动修改真实用户配置。首页不展示完整 Auto 表单。

新执行域按以下顺序决策：

1. 当前消息或历史消息存在非空图片 bytes：必须选择显式配置的图片模型，并且该模型的图片能力须为 `supported`；没有配置则返回明确错误。
2. 首条匹配的任务字段规则：选择其实际模型，记录命中的字段和值。
3. 请求推理强度为 `high`、`xhigh` 或 `max`，且配置了强推理模型：选择该模型。
4. 系统提示、当前内容、历史内容、工具定义和工具结果的字符总数达到长上下文阈值，且配置了长上下文模型：选择该模型。字符数不是 Token 数，不宣称精确计算上游上下文容量。
5. 无工具定义、无当前工具结果、无历史工具调用或工具结果、无非空图片、无高推理要求，且上述总字符数不超过短文本阈值，配置了快速模型：选择该模型。
6. 其余情况选择显式默认模型。可选能力角色未填写表示跳过该规则并继续匹配，最终无命中才使用默认模型；图片角色未填写则明确报错。明确配置的目标失效时返回错误，不静默改选其他目标。

用户确认同一聊天的新任务重新选模，连续工具回合保持模型。本地采用请求结构界定该边界：当前消息含 `toolResults` 时属于工具续轮，复用同一 `ContinuationStateKey` 已选的实际模型；当前消息不含工具结果时按新任务重新评估全部规则，即使历史中仍有以前的工具活动。实测请求的 `chatTriggerType` 在新输入与工具续轮中均为 `MANUAL`，不能单独用它识别新任务。此结构规则不进行自然语言语义分类，不声称复刻官方任务边界。

主会话和独立分支分别保存工具续轮模型，闲置一小时失效；重启后内存锁不保留。手动改选逻辑模型会清除对应 Auto 锁。工具续轮已选模型停用或删除，或新增图片与已选模型能力不兼容时，返回明确错误；新任务会重新按当前角色配置选模。单次执行失败不跨模型接管，同一模型配置的原有重试仍可执行。关闭策略后，旧角色引用的模型被删除或停用不阻断兼容默认路由；配置 JSON 损坏仍须明确报错。classifier 只读取当前非空执行域的记忆，未建立、过期或淘汰时不继承其他执行域；仅无执行域的兼容路径保留全局跟随。

路由日志记录 `auto_route_reason`、任务/分支字段与实际模型配置 ID；请求明细的 `dispatch_reason` 保留 `auto:<理由>` 并可附加执行层选择理由，`requested_model` 保留 `auto`，用量按实际模型价格计算。不得将完整用户提示词作为新增路由理由。

验收使用临时数据库、纯规则单元测试和本地 HTTP Mock，覆盖规则优先级、未知任务默认、错误目标、图片能力、会话/分支稳定性、手动模型隔离和实际候选计费；不调用真实收费模型。未部署新程序，未切换 capture/forward，未改变真实模型配置或数据库。
