# OpenAI Chat Completions 错误诊断与重试契约

## 目标与范围

本轮只调整 `provider=openai`、实际发往上游的路径为 `/chat/completions` 的请求。包括 Kiro 请求转换后的上游调用和本地 OpenAI 兼容入口的同协议转发；按实际 URL 判断，不能仅凭模型配置中的 endpoint 推断。其他 provider、OpenAI Responses、Codex、Anthropic 和 Gemini 的请求与重试行为不变。

首轮目标是让一次上游拒绝能关联到实际发送的工具定义和每次尝试，并避免把已确认的请求校验错误作为临时 503 重试。首轮证据不能确定 2026-09-29 的 `11129 invalid function call parameters` 由哪一个工具或字段触发，因此当时不自动删减、放宽或重写工具 schema，不调整 `strict`，不改变工具列表顺序及调用语义。后续复现所支持的有限兼容变换见文末。

## 可观察行为

1. 每次 OpenAI Chat 上游调用有一个稳定的本地请求关联 ID；同一逻辑请求的尝试、最终错误共用该 ID。日志记录实际 endpoint、尝试序号、外层 HTTP 状态、上游 request ID（如有）和可解析的内层错误状态/类型/代码。最后返回的错误响应随现有下游流程读取时解析；若下游提前关闭或错误体超过诊断上限，只记录已知字段并标记诊断不完整。新增诊断日志不记录 API Key。
2. 本轮新增的摘要日志为实际上游 `tools` 中的每个 function 记录顺序索引、名称、参数 schema 字节数和 SHA-256 摘要，另记录工具总数及整个出站工具数组摘要。摘要必须基于最终序列化的出站 body；新增摘要不保存 prompt、工具描述或 schema 正文。既有的转发 body 日志仍按现有 `log_detail` 配置工作：`summary` 可能保留请求前段，`full` 可能保留完整请求。该日志机制及其留存策略不在本轮修改范围内。
3. 只有远端响应能被可靠解析为“外层可重试 5xx、内层 `invalid_request_error` 且 HTTP 400”时，OpenAI Chat 的同一请求不按外层状态重试。仍原样保留该响应的外层状态、头和 body，供现有客户端错误转换路径使用。解析失败、响应体超限或超时以及其他状态沿用原有策略，不静默改判。
   Kiro 错误事件在这种情况下明确提示网关状态和内层请求校验状态，不再把它笼统描述为可稍后重试的临时 5xx；原始错误原因继续保留。
4. 重试判定读取错误 body 时必须有大小和时间上限，并恢复可供下游完整读取的已取得 body。已提交的 SSE 不被重放。对分组候选的切换策略，只有在确认共享错误分类契约和回归范围后才调整。

## 验收

- 用 Mock 上游复现含 `no_healthy_account` 与内层 `invalid_request_error`/400 的 503：只对目标 OpenAI Chat 路径停止同一请求重试，最终原始响应仍可读取，关联 ID、内外层错误字段与工具摘要可核对。
- 最后一次尝试及分组候选切换的错误体在被现有流程读取后可关联到同一请求 ID，记录内层错误字段且不改变响应内容或候选切换策略。
- 普通 503 仍按既有预算和次数重试；其他 provider 和 OpenAI Responses 行为不变。
- 工具诊断对正常、空数组、无参数、非法参数结构及大工具集合有稳定输出；不含消息正文、密钥或工具描述正文。
- 文档、代码和最小相关测试一致。真实上游是否接受某个工具 schema，需要在获得脱敏复现请求或远端日志后另行验收。

## 2026-09-30 复现与下一步兼容修复

新日志中的上游 request ID `438b522307065d79bdc8a1fe0da75492` 对应本地 trace ID `a8d61175-a4cd-4083-80f6-39f298cfa878`。该请求向 `/v1/chat/completions` 发送 101 个工具，上游返回外层 503、内层 `invalid_request_error`/400，代理只发送一次。随后移除 30 个 Chrome 工具的 71 工具请求仍失败；两次请求共有的 71 个工具定义摘要一致。因此原先的重试改动生效，但未修复上游的工具定义拒绝。

当前流量日志只保存请求体前段，不能还原所有 101 个完整 schema。可见的 `control_pwsh_process` 和 `execute_pwsh` 参数内有 `anyOf` 分支 `{"not":{}}`；按 JSON Schema 语义，这个分支永远不匹配，删去它不改变可接受的参数集合。Kiro 工具转换当前将该结构原样传给 Chat。下一步只对 Kiro→OpenAI Chat 的工具 schema 消去 `anyOf` 中这种恒假分支，并在包装没有其他字段时折叠单分支。Responses、Anthropic、Gemini 和本地 Chat 原样透传入口不受此兼容变换影响。工具摘要额外记录各 schema 的结构关键字计数，以便日志正文被截断时仍可定位剩余异常；不记录属性名、描述或取值。该变换是基于可见证据的最小兼容尝试，不保证上游没有其他未记录的拒绝条件；必须通过真实请求另行验收。

### 真实上游探针后的修正

2026-09-30 使用现有 `deepseek-v4.1-flash` 配置进行了共 14 次获授权的最小诊断请求，消息均为 `OK`，`max_tokens=1`。无工具、1 个及 71 个简单工具、单独的 `anyOf`／联合 `type`／`$ref`、日志中可还原的前 6 个真实工具（修补前后）、71 个长描述工具、71 个混合复杂 schema 工具，以及前 6 个真实工具加 65 个测试工具都返回 HTTP 200；故意设置无效 JSON Schema 类型的对照请求返回 HTTP 503。这些结果排除了简单的工具数量、请求体字节数、前 6 个工具和上述单项特征作为充分触发条件，不能证明剩余 65 个工具中具体哪个有问题。删除 `{"not":{}}` 分支未修复用户请求，不能再称为根因修复。

完整捕获发现 `todo_list.new_tasks.items.$ref` 指向 `tasks/anyOf` 的嵌套分支；前述 `anyOf` 清理会删除或折叠该引用路径，却不改写 `$ref`，使原本可解析的引用在出站 schema 中失效。为避免该回归，含 `$ref` 的单个工具 schema 暂不进行 `{"not":{}}` 清理；其余工具仍按现有规则处理。这只能修复本地转换引入的断链，原始 `11129` 在清理实施前已经出现，需复现后继续定因。

引用安全改动后再次复现，`todo_list.new_tasks.items.$ref` 仍指向 `#/properties/tasks/anyOf/0/anyOf/1/items`，但同一 schema 的 `tasks` 只有 `type: ["array", "null"]` 和 `items`，没有 `anyOf`。这说明进入本地清理前的工具定义本身已带有悬空引用；完整 71 个出站工具中只发现这一处无法解析的本地 `$ref`。仅当工具名为 `todo_list`、旧引用路径精确匹配、`tasks.anyOf` 不存在且 `tasks.items` 是对象 schema 时，OpenAI Chat 出站把该引用改为 `#/properties/tasks/items`；其他工具、其他路径和非 Chat 协议不改。修复后仍须用原 Kiro 请求验证上游结果。

修复版在同一 Kiro 对话中于 02:34 至 02:35 连续 5 次收到上游 HTTP 200，流式结果均完成，且包含工具调用；用户确认原操作恢复正常。失败和首次成功请求都发送 71 个工具，逐项参数摘要对比只有索引 68 的 `todo_list` 发生变化。这是对该故障路径的真实验收，不代表已验证其他模型或其他客户端。当前本机运行的是带 `desktop dev` 标签的诊断构建；正式桌面版的授权服务按版本和二进制 SHA-256 校验，不能把未登记的新正式构建直接替换运行版。

现有流量日志把 159061 字节的失败请求截断到前 65536 字节，仅能还原前 6 个工具。下一次实际 OpenAI `/chat/completions` 上游响应被完整读取、且可确认错误码 `11129` 时，额外把该次出站请求的工具名称和完整 `parameters` schema 写入流量日志同目录下的 `captures/openai-chat-11129-<trace_id>-attempt-<序号>-<随机后缀>.json`。同一请求的多次尝试分别保存。捕获不复制请求消息、认证 header 或函数顶层描述；**schema 本身可能包含描述、默认值等敏感文本**，文件须作为私有诊断数据处理。无工具、错误体未读完整、流量日志未落盘或写入失败时不保存；不改变上游响应或重试判定。诊断捕获仅适用于实际 OpenAI Chat 上游请求及该错误码。
