# Auto 职责细分观察日志

## 目标与范围

先积累真实 Auto 使用证据，再决定普通 Vibe 是否能按稳定协议字段或工具行为进一步细分。日志只描述客户端提供的信息和代理的实际选择，不推断职责，不改变路由、continuation 锁、activity 状态或用户配置。

已有 `auto-routing` 流量日志保留原契约。新增独立 JSONL 文件，位置为现有 `proxy.log_file` 路径加 `.auto-diagnostic.log`；默认即 `kiro_traffic.log.auto-diagnostic.log`。复用现有文件轮转：单文件最多约 100 MiB，保留当前文件与 `.1`，合计约 200 MiB。保留时长取决于使用量，不承诺天数。独立文件同步追加，不经过正文日志的异步队列，避免队列拥塞丢失或正文挤占保留空间。初始化、写入和轮转失败沿用明确错误日志；原有 `log_file` 为空时不创建文件。没有新增开关。

## 记录内容

- 每条带 `schema_version=1`、进程运行标识、事件 ID 与时间。运行标识区分重启；会话、continuation、execution 标识使用 SHA256 关联键，不保存原始值。哈希用于关联，不等于匿名化。
- `route_selected`：协议、模式、客户端显式 task_type、工作流来源与节点路径、选择来源与未匹配原因、实际模型/分组、effort、锁作用域、原生 continuation 来源，以及请求结构摘要。记录选择不代表上游成功。沿用现有记录时点：单模型在转发前记录，分组在转发返回后记录实际成员；失败分组不虚构已选成员，不用选择事件数直接推算请求数。
- `request_result`：通过同一请求的 `request_id` 关联选择记录，记录路由解析失败、无目标、授权阻止、转发失败或上游响应头到达及状态码和耗时。只记录固定阶段，不记录原始错误正文；响应头到达不代表流已成功完成，不提前读取响应流。分组转发失败仍有结果事件。
- raw Responses 结构摘要：完整 input 的项目数、固定类别/角色计数、工具调用与结果数、末尾最多 12 个工具调用名、最多 32 个工具定义名、最多 64 个 metadata 键名及超限数量。历史中的工具结果不被标作本轮 continuation。工具参数、结果正文、提示文本与 metadata 未知值均不记录；无法解析时明确标记摘要不可用，不改变请求结果。
- Kiro 结构化请求摘要：历史条数、当前/历史工具结果与调用数、当前文本及系统文本字节数、图片数、工具定义名和末尾调用名。仅在解析结果明确提供本轮工具延续标记时记录其值，未知与 false 分开。
- 工具名和 metadata 键名有长度/字符约束，非法名称仅记录摘要标识；列表有界并记录省略数量。枚举外 input 类型/角色仅计入 `other`。
- `activity_batch`：固定解析类别、解析/消费状态、可提交会话候选数、实际更新数、因既有顺序规则未更新数；最多 16 个候选会话的关联键、节点路径和 seq。候选数不是原始活动数；部分解析失败时不宣称任何状态已提交。无 workflow 的活动仍只记录固定原因，不保存正文。
- `activity_lookup`：沿现有查询路径记录无观察、模式不兼容、合成头无效或成功合成，以及已有观察的 seq 和年龄；按会话与 continuation 关联键连接后续选择记录。成功合成不代表 continuation 最终改用该观察，路由仍遵守原有锁。

## 使用与验证

启用新构建后正常使用即可。后续分析时一起读取诊断当前文件与 `.1`，按会话与 continuation 关联键观察默认目标占比、规则未匹配原因、工具行为、节点证据与状态采纳情况。既有普通流量日志可能含正文；新增独立日志不复制这些正文，收集诊断文件无需打开全量正文记录。

结构统计可以帮助发现可用信号，无法独自证明任务应该属于哪个职责。判断细分质量仍需要有代表性的实际任务及用户预期；本轮不新增分类器或反馈界面。

验证要求：用固定 Mock 覆盖 raw/结构化请求、未知与非法字段、有界列表、敏感正文不落盘、正常与失败 activity、顺序未更新、独立轮转、队列拥塞、并发关闭及重启追加；保留原路由测试。最终构建不自动替换正在运行的代理。
